# Releases and environments (2026-11-18)

> **Status: DECIDED, built in two PRs.** The owner delegated these
> decisions (2026-11-17): conventional commits, semantic versions, a
> staging environment deployed on every merge to `main`, and production
> deployed from a release only after the owner approves. PR 1 (conventions
> and releases) needs no cloud. PR 2 (environments and deploys) needs the
> owner's one-time steps in `docs/production-deploy.md`, «Environments and
> releases», before its first run.

## The problem

Nothing has ever been deployed. `docs/production-deploy.md` describes a
careful manual deploy from the owner's terminal into ONE project, and it
tells the owner to edit `environment.production.ts` by hand, and not commit
it, to build for staging. There is no version: `package.json` says `0.0.0`,
and the client issue sink's `release` field is `null` on every issue. There
is no changelog, no tag and no record of what is live.

The owner is one developer working through AI agents. Agents open most PRs.
So whatever ships must be decided by the repository, not by whoever is at
the keyboard, and the two irreversible acts — a release and a production
deploy — must wait for the owner.

**The hard constraint.** The Firebase projects `creativo-prod` and
`creativo-staging` run the owner's OLD React app, live. Nothing here may
deploy to, read from, configure or reuse them. A data migration from them is
planned later, so project ids stay configuration (GitHub Environment
variables and the committed per-environment web config), never code.

## Decisions

### Branches, commits and versions (PR 1)

| #   | Question                           | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R1  | Which branches?                    | Trunk-based. `main` is always releasable. Work happens on short-lived `feat/…`, `fix/…`, `chore/…` and agent (`claude/…`) branches, one PR each. There is no `develop` branch and no branch per environment: **staging is `main`, production is the release tags.** A `release/vX.Y` branch exists only for the rare hotfix (R14).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| R2  | How does a PR land?                | **Squash merge only.** One PR is one commit on `main`: its subject is the PR title, its body the PR description (`squash_merge_commit_title: PR_TITLE`, `squash_merge_commit_message: PR_BODY`). Merged branches are deleted. `tools/ops/github-repo-settings.sh` prints the settings; the owner applies them.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| R3  | What does a commit say?            | A [Conventional Commit](https://www.conventionalcommits.org/): `type(scope)!: subject`. Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `revert`. A scope is lower-case (`team`, `identity`, `ui`, `deps`). A subject may start with a name («Apple Health columns»): the conventional preset's subject-case rule is off. A breaking change is marked by `!` after the type or scope, or by a `BREAKING CHANGE:` footer. The header may be 160 characters: the repository's titles run long by taste, and all 99 conventional PR titles in its history pass. `CONTRIBUTING.md` says this for humans.                                                                                                                                                                                                                                               |
| R4  | Who checks it?                     | Two places, one rule set (`commitlint.config.mjs`). The PR title, by a **required** check (`.github/workflows/pr-title.yml`, job `pr-title`), because the title IS the commit on `main`. Local commits, by a husky `commit-msg` hook: advisory in effect, since the squash rewrites them, but it catches a bad habit early. The title check is its own workflow because a title edit must re-check, and `ci.yml` re-running seven jobs on every edit would waste half an hour of runner time.                                                                                                                                                                                                                                                                                                                                                                                        |
| R5  | One version, or one per app?       | **One version for the whole product.** The web, the functions and the rules ship together and share one wire, so one number names one state of all of them: the root `package.json`, one `CHANGELOG.md`, tags `vX.Y.Z`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| R6  | Who decides the number?            | **release-please** (`googleapis/release-please-action`), from the commits since the last tag. It keeps one release PR open (`chore: release X.Y.Z`) that updates `package.json`, `CHANGELOG.md` and `.release-please-manifest.json`. Merging that PR is the release: it tags `vX.Y.Z` and writes the GitHub Release. **Pre-1.0 until launch** (`bump-minor-pre-major`): a breaking change bumps the minor, a `feat` the minor, a `fix` the patch. The first release is `0.1.0` (`initial-version`): without it, release-please starts a `0.0.0` manifest at `1.0.0`. Launch is a commit with the footer `Release-As: 1.0.0`.                                                                                                                                                                                                                                                         |
| R7  | What does the changelog show?      | Features, Bug Fixes, Performance and Reverts. Refactors, docs, tests, build, CI and chores are hidden: they change nothing a person using the app notices. The first release starts after the commit this ADR lands on (`bootstrap-sha`), not at the 300 commits of history before any release existed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| R8  | Which token runs release-please?   | **A GitHub App's installation token**, minted per run by `actions/create-github-app-token`. A PR or tag created with `GITHUB_TOKEN` triggers no workflow, so CI would never run on the release PR, the `main` ruleset would block it forever, and the tag would never start the production deploy. A personal access token would work but is tied to a person, long-lived and broad. The App has three permissions on this repository only: contents, pull requests and issues (labels), read-write. Its client ID is a repository variable (`RELEASE_APP_CLIENT_ID`, public), its private key a repository secret (`RELEASE_APP_PRIVATE_KEY`).                                                                                                                                                                                                                                      |
| R9  | How does a build know its version? | **A release stamp, compiled in.** `tools/release/release-stamp.mjs` computes it once per deploy: `0.4.1` for a build of the tag `v0.4.1` (and it refuses a tag that disagrees with `package.json`), `0.4.1+abc1234` for a build of a branch commit — the 0.4.1 manifest at that commit, so unreleased commits since 0.4.1 included. The web gets it as an esbuild `define` (`CREATIVO_RELEASE`, `libs/infrastructure/firebase-app/src/lib/web-release.ts`): a literal in the bundle, no global and no fetch. Every client issue carries it as `release`, which Error Reporting shows as the version. The functions get it as one more line of the generated `.env.<project>` (`CREATIVO_RELEASE`, `tools/flags/write-functions-env.mjs --release`), and every server log line carries it as `release`. A build without one (local, the emulators, the tests) reads `null`, as today. |

| E1  | Which environments?                              | Three. **development** is the emulators under `demo-creativo-test`, unchanged. **staging** and **production** are two NEW Firebase projects on Blaze, suggested ids `creativo-v2-staging` and `creativo-v2-prod` (the owner picks; ids are global). Each is a GitHub Environment of the same name.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| E2  | Build once, or once per environment?             | **Once per environment, from the same commit.** The repository already compiles an environment in: `fileReplacements` swaps the environment file, the flag map is a named JSON import so the bundle carries only its own map, and the preflight's P4 and P10 judge literals in the built bundle (the project id, the App Check site key). Promoting one artifact would mean reading the web config from Hosting's `/__/firebase/init.json` and the flags at run time: one more request on the boot path before Firebase, App Check and the issue reporter can start, and a file the service worker must cache and revalidate. The owner's bar is that loading is invisible. Two builds of one commit differ only in the environment file, the flag map and the stamp; the lockfile and the code are the same. Revisit if a third environment appears.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| E3  | How is a staging build made?                     | A `staging` configuration of `web:build` (`apps/web/project.json`): production's budgets, hashing and service worker, with `environment.staging.ts` swapped in. That file has production's shape, the `staging` flag map and its own App Check site key slot. It replaces the advice to edit `environment.production.ts` temporarily. The functions read the `staging` map when `FLAGS_ENV=staging` (the flags writer, unchanged).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| E4  | When does staging deploy?                        | **After CI succeeds on a push to `main` or to `release/**`** (`.github/workflows/deploy-staging.yml`, `workflow_run`). One deploy at a time, never cancelled once it runs; GitHub keeps one queued run, so a newer merge replaces an older queued one and staging jumps to the newest `main`. **Departure from the brief:** the brief deployed `release/*` pushes directly. CI now runs on `release/**` pushes too and the deploy waits for it, so a hotfix reaches staging through the same gate as `main`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| E5  | When does production deploy?                     | **On a release tag `v*`** (`.github/workflows/deploy-production.yml`, `push: tags`). The `production` environment requires the owner's approval and admits only tags `v*`. The job checks out the tag, refuses unless the tag's commit passed CI and the tag matches `package.json`, builds, runs the preflight, deploys and smoke-checks. The repository is public, so environment protection rules cost nothing. A tag ruleset lets only the release App create, move or delete a `v*` tag.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| E6  | What does a deploy do, in what order?            | The runbook's ordinary order (`production-deploy.md` §3), non-interactive: the preflight in both scopes first (all but P2 and P3, which only the index deploy can satisfy when a release adds an index), then Firestore indexes and TTL, a bounded wait until the preflight's P2 and P3 pass, Firestore and Storage rules, functions, then hosting straight after. Then a smoke check: the site answers, serves the new stamp in its main script, routes a deep link and serves the CSP. **CI never passes `--force`:** a deploy that would delete a function, raise the minimum bill or drop an undeclared index stops and names the command. Those are the owner's deliberate acts (§5, §6).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| E7  | How does production roll back?                   | **The same workflow, dispatched from an older tag** (`workflow_dispatch` with that tag as `tag`, run from the tag itself). The `production` environment's tag rule and the identity's ref condition both read the run's ref, so a dispatch from `main` can never reach production, and the approval is the same. The run deploys that tag's code with that tag's workflow. A newer release that added a function makes the rollback stop at the deletion (E6): Hosting's own one-click rollback is the fast path for the web, and the deletion stays the owner's call.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| E8  | How does CI reach Google Cloud?                  | **Workload Identity Federation**, never a JSON key (`google-github-actions/auth`, pinned to a full commit SHA). Per project, `tools/ops/deploy-identity.sh` (dry run by default) creates a pool and a GitHub OIDC provider whose condition admits only this repository's id and that environment — and, for production, only refs `refs/tags/v*` — plus one deploy service account that only that environment's jobs may impersonate: the principal set of the mapped attribute `repository_environment` (`<repository id>/<environment>`), never the token's subject — GitHub's immutable subjects (`repo:<owner>@<id>/<name>@<id>:…`, the default for this repository) never matched a classic `repo:<owner/name>:environment:<env>` binding, and the first staging deploy was refused `iam.serviceAccounts.getAccessToken` (amended 2026-11-18). The account's roles are what firebase-tools 15.34 asks for: Hosting, rules, indexes, functions (with Cloud Run, for the callables' invoker), Cloud Scheduler, Secret Manager read, Artifact Registry read, the preflight's reads, and actAs on the runtime account only. The bindings a first deploy would otherwise grant itself (the service agents' roles, the runtime account's access to the four secrets, the Storage rules agent's Firestore role) are granted by the script, so the deploy account never edits the project's IAM policy. So is the runtime account's Token Creator role on itself, which custom-token sign-in needs (`createCustomToken` signs through IAM with no key file); the script enables the Compute Engine API, which creates that account in a new project, and waits for it. The first staging deploy proves the list; a missing permission names itself in the log. |
| E9  | Where do ids and secrets live?                   | GitHub Environment **variables** (not secrets): `FIREBASE_PROJECT_ID`, `GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_DEPLOY_SERVICE_ACCOUNT` — none of them grants anything alone. The runtime secrets (`OTP_POSTMARK_TOKEN`, `OTP_EMAIL_FROM`, `WALKIN_ID_KEY`, `LOG_DIGEST_KEY`) stay in each project's Secret Manager, set once by the owner; they never pass through GitHub or CI. The public web config stays committed, per environment. No workflow uses `pull_request_target`; a fork's PR gets no credential.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| E10 | How does one `firebase.json` serve two projects? | **The deploy points the checkout at its project** (`tools/release/deploy-target.mjs`, run in the CI runner's throwaway checkout). `firebase.json`'s CSP names ONE callables host and the CSP gate and P5 refuse a second, so one committed file cannot serve both projects. This is the repository proving the brief's shape incomplete: the CSP, not only the web config, is per project.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

A spec fails if any config, workflow or environment file names either id outside those refusals.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

### Hotfixes

| #   | Question                              | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| --- | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R14 | How does a fix reach production fast? | **Default: like everything else.** A `fix:` PR to `main`; unreleased features ride along dark, because each environment's flag map keeps them off; staging deploys; release-please's PR now proposes the patch; merging it tags; the owner approves production. **Rare: a release branch**, only when `main` holds work that must not ship yet and cannot be kept dark. Cut `release/vX.Y` from the tag (`git push origin vX.Y.Z:refs/heads/release/vX.Y`), land the fix on `main` first, then cherry-pick it in a PR to the release branch. release-please runs on that branch too and opens `chore(release/vX.Y): release X.Y.Z+1`; its tag deploys like any other. Because the rare path is taken only when `main` holds a `feat`, `main`'s next release is a minor and never collides with the patch. |

## Rejected

- **A `develop` branch, or one branch per environment.** Two long-lived
  branches drift, and every fix lands twice. Trunk-based with tags gives the
  same three states with one branch.
- **Build once and promote.** See E2: a run-time config fetch on the boot
  path, against an invisible-load bar, to save one build per release.
- **`semantic-release`.** It releases on every merge. A release PR lets the
  owner choose when to cut one, and shows the changelog before it exists.
- **Changesets.** It suits many packages published to npm; this is one
  product that publishes nothing.
- **A personal access token or `GITHUB_TOKEN` for releases.** R8.
- **JSON service-account keys.** A long-lived secret that leaks with a log
  line. WIF tokens live an hour and only this repository's environment jobs
  can mint them.
- **Deploying staging straight from `release/*` pushes.** E4.
- **`--force` in CI.** E6.
