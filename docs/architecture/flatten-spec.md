**Why `EndMinute` (decision F-1):** the locked `[0, 1440)` range of
`MinuteOfDay` cannot hold the end of a shift, a day window or an exception
range that runs to midnight, which today's data allows (`ShiftSegment`,
`DayWindows.is` and `ExceptionEffect` ranges accept `endMinutes === 1440`).
A second brand keeps the locked range intact and makes "this is an
exclusive end" a type. Every stored `endMinutes` / `closeMinutes` field is
`EndMinute`; every `startMinutes` / `openMinutes` is `MinuteOfDay`.

### 1.3 `LocalDate` civil math (integer algorithms, no `Intl`, no `Date`)

The companion absorbs `DayKey` (`day-key.data.ts`) and layer 3 of today's
`ZonedTimeSystem`. Algorithms: Howard Hinnant's `days_from_civil` /
`civil_from_days` (today's `DayKey.epochDayOf` / `fromEpochDay`, moved
verbatim), ISO weekday `((epochDay + 3) mod 7) + 1`.

function idCompanion<B extends string>(brand: B) {

### 2.1 The new `ZonedTimeSystem` (ingestion only)

`zoned-time.system.ts` keeps native `Intl` (`formatToParts`, `hourCycle:
'h23'`) and its `Map<TimeZone, Intl.DateTimeFormat>` cache — the only

```ts
export const ZonedTimeSystem = {
  /** The TimeZone smart constructor (F-2): accepted by Intl.DateTimeFormat. */
  checkZone(raw: string): Result<TimeZone, TimeError>,

  /** Shop wall clock → the instant (ingestion). Spring-forward gap →
   *  DST_GAP_INVALID_TIME; fall-back repeat → the EARLIER offset (locked). */
  toUtc(localDate: LocalDate, minute: MinuteOfDay, timeZone: TimeZone):
    Result<UtcEpochMs, TimeError>,

  /** The instant → the shop wall clock (total: every instant has one). */
  toLocal(utcEpochMs: UtcEpochMs, timeZone: TimeZone): WallTime,

  /** "Now" for systems — derived ONCE per request at the boundary. */
  shopNow(utcEpochMs: UtcEpochMs, timeZone: TimeZone): ShopNow,

  /** The first instant of a shop day (a midnight inside a gap resolves to the
   *  gap's end) — for day-boundary lifecycle comparisons (T3). Total. */
  startOfLocalDay(localDate: LocalDate, timeZone: TimeZone): UtcEpochMs,

  /** ISO-8601 WITH an explicit offset → the instant (legacy stored/wire
   *  strings in shims; specs). No offset → TIME_INVALID_DATE_TIME. */
  parseOffsetIso(iso: string): Result<UtcEpochMs, TimeError>,

  /** The instant as ISO-8601 in the zone with its offset
   *  ('2026-10-10T14:00:00.000+03:00') — .ics and the edge's legacy wire
   *  params, byte-identical to today's ZonedDateTime.toISO(). */
  toIso(utcEpochMs: UtcEpochMs, timeZone: TimeZone): string,
} as const;
```

### 2.3 The time rules every group applies

- **T1 — placement math is local.** Collision, packing, availability,
  roster windows, busy projections, calendar grids, day bucketing, "is it
  today", "is it upcoming" — only `LocalDate` + `MinuteOfDay`/`EndMinute`
  (+ `ShopNow.localDate`/`currentMinute`). A system never reads `*UtcMs` for
  these.
- **T2 — lifecycle comparisons on stamps — DECIDED 2026-10-11: ruling (a), Law 7.3 amended ("never for placement math"); the rows below compare and add `UtcEpochMs` stamps, and the (b) follow-up commit is NOT made.**
  Law 7.3 keeps `utcEpochMs` for range indexes, crons and `.ics`, and lets
  `ShopNow.utcEpochMs` only STAMP lifecycle instants. Today's product
  measures the rows below in ELAPSED real time. No group implements them
  before the owner rules:
  - **(a) Law 7.3 amended to "never for placement math"** (foundation
    lands the owner's sentence in `CLAUDE.md` and `AGENTS.md` with a
    pointer to this list). These rows, and ONLY these, compare or add
    `UtcEpochMs` values, with `UtcEpochMs.compare`/`plus*` as the only
    arithmetic. TTL and expiry: `otp` (`expiresAtUtcMs`, the resend
    window), `impersonation`, `coupon-grant` (`grantExpiresAtUtcMs`),
    `coupon-expiry.isWithin`, `discount.inputsFromGrants`, `voucher`
    redeemability (`expiresAtUtcMs`; `spendable` is T5, on `LocalDate`),
    `account-status.isBlockedAt`, `client-glance.pauseOf`. The cancellation
    window: `cancellation-policy` (`deadlineUtcMs`, `allowsFreeCancelAt`,
    `isLateCancellation`, `mayCancel`/`mayMove`), `booking-policy`'s
    companion, `client-stats-policy.isLateCancellation`, the `client-stats`
    late-cancel facts (T9). Statistics: `appointment-lifecycle`
    `latenessMinutes` / `bookingLeadTimeMinutes`, `achievements` on-time.
    Staleness and budgets: `policy-recompute-job`, `trigger-attempt`
    (`eventAgeMs`), `work-budget.isSpent`. Cooldowns:
    `waitlist.cooldownSinceUtcMs`, `HasRecentNotification(… sinceUtcMs)`.
    Stamp ordering: `standing.isNewSince`,
    `visit-story.decisiveCancellationIndex`, `client-stats.projectionClock`.
  - **(b) Law 7.3 stands as written.** The flatten commit still ships the
    (a) shapes (behaviour is frozen in it). The follow-up commit of §0.2
    deletes `UtcEpochMs.plus*` and `TimeCoordinate.seatStartUtcMs` and
    re-expresses every row above on the civil line: a deadline is
    `(localDate, startMinutes)` minus `windowHours · 60` minutes, carried
    across days with `LocalDate.addDays`, compared with
    `(now.localDate, now.currentMinute)`; a TTL is a stored `…LocalDate` +
    `…Minutes` expiry; a statistic is a `MinuteDelta` between two wall-clock
    points (T6). A location-less row (OTP, impersonation, account block)
    builds its `ShopNow` from the `ShopLocation` named by
    `TenantConfig.defaultLocationId` (F-4). Results move by up to 60
    minutes on the two DST nights, which is why it is its own commit.
- **T3 — a shop-day boundary as an instant** (a voucher is spendable "from
  the first instant of today") is computed at the boundary with
  `ZonedTimeSystem.startOfLocalDay` and passed in as a `…StartUtcMs:
UtcEpochMs` parameter — or, preferably, replaced by a stored
  `*LocalDate` sibling (T5).
- **T4 — "now".** A system that compares now with local coordinates takes
  `now: ShopNow`; a system that only stamps or compares lifecycle instants
  takes `nowUtcMs: UtcEpochMs` (decision F-5: an OTP or a profile audit has
  no location, so it has no shop clock). Under G-1(b), `nowUtcMs` survives
  only as a stamp source and every comparison takes `now: ShopNow`. No
  system takes `nowMs: number` any more. `TxPorts.nowMs: () => number` → `nowUtcMs: () => UtcEpochMs`.
- **T5 — a stamp a system buckets by shop day carries its day.** Where a
  system groups or compares a lifecycle stamp with a `LocalDate` (ledger
  months, medal "earned on" days, voucher "spendable today", season
  announcement notice), the stored struct carries a `…LocalDate` beside the
  `…UtcMs`, both written at the boundary from the same `ShopNow`. In this
  pass the shim derives it with `ZonedTimeSystem.toLocal(stampMs, zone)`.
- **T6 — a stored instant a placement check needs** (an arrival stamp
  against a seat's end) is converted at the boundary with `toLocal` and
  handed to the system as a `WallTime` parameter.
- **T7 — one shop day per appointment.** Every seat of an appointment
  starts on the appointment's `localDate` and its sold end is ≤ 1440
  (decision F-6; today's data has no visit crossing midnight — the shop
  hours close before it). A busy span's padded chair time is clipped to
  `[0, 1440]` in the projection, as `ZonedTimeSystem`'s day table clipped it
  today. A shim that meets a legacy appointment violating F-6 returns
  `BOOKING_INVARIANT_VIOLATED` (none exists; the booking-core group greps
  the seed and e2e fixtures to prove it).
- **T8 — multi-day spans are `LocalDate` arithmetic** (recurrence,
  capacity months, client-stats windows, streaks, tiers, rewards). A
  rolling window "the last N days, now included" compares
  `(localDate, startMinutes)` pairs lexicographically against
  `(LocalDate.addDays(now.localDate, −N), now.currentMinute)` — equal to
  today's `nowMs − N·86 400 000` comparison except within one hour of the
  edge when exactly one DST transition lies inside the window.
- **T9 — a seat's start instant (G-1(a) only)** (late-cancel judgement per
  seat) is `UtcEpochMs.plusMinutes(appointment.utcEpochMs,
MinuteDelta.between(appointment.startMinutes, seat.startMinutes))` via
  `TimeCoordinate.seatStartUtcMs` — exact for every visit that does not
  straddle a 03:00/04:00 transition (none can: the shop is closed then).
  Under G-1(b) the follow-up commit deletes it and judges the seat on
  `(appointment.localDate, seat.startMinutes)`.
- **Exception (owner-acknowledged, flip 2) — the age check's day is the UTC
  civil date**, not a shop day: `completeRegistration`, `updateProfile` and
  the web's profile and onboarding stores judge the 16–120 window on
  `ageDay: LocalDate = ZonedTimeSystem.toLocal(now, UTC_ZONE).localDate`,
  derived ONCE at the boundary (`UTC_ZONE` of `@core/pipelines`), as every
  writer does today; `ProfileEditSystem` and `AgeSystem` take only that
  `LocalDate`, never an instant, and no document stores a zone (Law 7.2).
  Kept until the owner rules on `docs/architecture/flips/flip-2-identity.md`
  §10.1 (F2-7): the UTC day, or the default shop's wall-clock day.

## 4. ERROR CODES — the shared surfaces are foundation's

### 4.1 Rules

- Every error struct: `code` → **`errorCode`** (N12). Every other field is a
  flat i18n parameter; a parameter typed by a renamed tag takes the new tag
  type; time and money parameters follow N2–N6 (`startMs` →
  `localDate` + `startMinutes`, `amountMinorUnits` → `amountCents`).
- Values: SCREAMING_SNAKE, prefixed by the dictionary's domain. The general
  form drops the dots of the old code and upper-snakes camelCase
  (`booking.staffEdit.forbidden` → `BOOKING_STAFF_EDIT_FORBIDDEN`). Two
  owner-locked departures: the booking commit dictionary drops `COMMIT`
  (`booking.commit.slot_unavailable` → **`BOOKING_SLOT_UNAVAILABLE`**, the
  law's own example) and `time.nonexistent_local_time` → **`DST_GAP_INVALID_TIME`**.
  `repo.*` / `repository.*` unify under `REPOSITORY_`;
  `appointment.not_arrivable` takes its dictionary's prefix
  (`SCHEDULING_APPOINTMENT_NOT_ARRIVABLE`).
- Dictionary renames (F0): `BookingCommitErrorCode` → `BookingErrorCode`
  (and `BookingCommitError` → `BookingError`, file `booking-errors.data.ts`).
  Every other dictionary keeps its name; the systems' own dictionaries
  (`StaffEditErrorCode`, `MoveErrorCode`, `CancellationRefusalCode`) stay in
  their system files.
- **New dictionary** `PrimitiveErrorCode` (§1.1); its i18n keys are new
  (generic text: "Invalid value.").
- Per-variant refinement vocabularies that are i18n key SEGMENTS and wire
  params keep their values (§0.4 extension): `BookingErrorField`
  (`locationId`, `person_overlap`, `guest_label`), `ShopUnavailableReason`,
  `CarriedSeatRefusal`, the streak rule field locators on the wire
  (§3.5).

## 5. D29 — CUSTOMER vs USER (appended to blueprint §9 on 2026-10-10)

### 5.1 The decision

> **D29 — the client record and the auth account are two entities.**
> `UserId` is the Firebase Auth uid and `users/{uid}` is the ACCOUNT
> (sign-in, roles, claims, contact used to sign in, inbox). `CustomerId` is
> the CLIENT RECORD the shop keeps about a person it serves —
> `customers/{customerId}` — whether or not that person has an account. A
> customer MAY reference an account through the explicit nullable field
> `userId`; the two ids are never the same value and never assignable to
> each other.

**Recommendation: (a) separate `customers` collection, deterministic id
for account holders.**

| Option                                                                                                                                                                                                                    | Shape                                                                                                                                                         | Verdict                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **(a) `customers/{customerId}`, `customerId = CustomerId.forUser(uid)` for an account holder, a random `cus_…` id for a walk-in (superseded by OR-26: `CustomerId.forWalkIn`, deterministic over the walk-in's contact)** | the record is created idempotently inside the transaction that first needs it (`tx.get` by a derivable path, no query); the link is the stored `userId` field | **recommended** — no query inside a transaction, an id that never equals the uid, and walk-ins without accounts get records |
| (b) `customers/{random}` for everyone, found by `where('userId', '==', uid)`                                                                                                                                              | a single-field query to resolve an account's record                                                                                                           | a query in every booking transaction; a race creates two records for one account unless a second lock document exists       |
| (c) keep the uid as the client key (status quo)                                                                                                                                                                           | `clientStats/{uid}`, `subjectUserIds`                                                                                                                         | violates the locked rule ("never a shared value used as both"); a walk-in can never have stats, loyalty or photos           |

### 5.2 `customer.entity.ts` (identity, new)

```ts
/** customers/{customerId} — the shop's record of a person it serves. */
export type Customer = {
  readonly id: CustomerId;
  /** The account this person signs in with; null for a walk-in the shop entered. */
  readonly userId: UserId | null;
  /** The name the shop calls them — the account's full name at link time, or what the desk typed. */
  readonly displayName: string;
  readonly phone: E164 | null;
  readonly email: Email | null;
  /** Lower-cased display name + prefixes, as on users (SearchFieldsSystem). */
  readonly searchName: string;
  readonly searchPrefixes: readonly string[];
  readonly createdAtUtcMs: UtcEpochMs;
  readonly customerOrigin: CustomerOrigin; // 'REGISTRATION' | 'STAFF_WALK_IN' | 'FIRST_BOOKING' | 'SEED'
};
```

Companion in `components/customer-origin.data.ts` (identity): the
`CustomerOrigin` dictionary, typing the field `customerOrigin` (N15 — not
`createdBy`, which reads like an actor id). Field rule: contact on a customer is the
SHOP's copy (what the desk may edit); the account's sign-in contact stays on
`users/{uid}` (OQ-5: whether the two are synchronised by a trigger).

### 5.3 Who creates it

- **Registration** (`completeRegistration`, identity flip (2)) creates BOTH:
  it finishes `users/{uid}` and creates `customers/{CustomerId.forUser(uid)}`
  with `userId = uid`, `customerOrigin: 'REGISTRATION'`, in the same commit plan
  (the users stub replay rule already handles `REPOSITORY_ALREADY_EXISTS`).
- **Staff walk-in with a name** (the visit editor's «Нов клиент») creates
  ONLY a customer (`userId: null`, `customerOrigin: 'STAFF_WALK_IN'`, a random
  id from `nextId`). A walk-in without a name stays an `ANONYMOUS` seat with
  a `guestLabel` and no record — today's behaviour.
- **First booking of an account holder with no record yet** (every account
  registered before flip (2), and every dev-seed client): the booking
  pipeline creates `customers/{CustomerId.forUser(uid)}` inside the commit
  transaction (`customerOrigin: 'FIRST_BOOKING'`), idempotent by the
  deterministic id.
- **Seed** writes a customer per seeded client (`customerOrigin: 'SEED'`).
- Linking a walk-in record to an account that registers later is a merge
  (D26's design-only "merge/claims") — out of scope; until then the two
  records stay separate.

### 6.1 `WriteOp` after Law 6 (`write-op.data.ts`)

```ts
export const WriteAction = {
  Set: 'SET',
  Create: 'CREATE',
  Update: 'UPDATE',
  Delete: 'DELETE',
} as const;
export type WriteAction = (typeof WriteAction)[keyof typeof WriteAction];

export namespace WriteOp {
  export type Set = {
    readonly writeAction: typeof WriteAction.Set;
    readonly path: DocPath;
    readonly body: DocBody;
  };
  export type Create = {
    readonly writeAction: typeof WriteAction.Create;
    readonly path: DocPath;
    readonly body: DocBody;
  };
  /** Root fields only. `deleteFields` names root fields to remove (FieldValue.delete()). */
  export type Update = {
    readonly writeAction: typeof WriteAction.Update;
    readonly path: DocPath;
    readonly fields: DocBody;
    readonly deleteFields: readonly string[];
  };
  export type Delete = {
    readonly writeAction: typeof WriteAction.Delete;
    readonly path: DocPath;
  };
}
```

- `WriteKind` → `WriteAction` (field `kind` → `writeAction`), values
  SCREAMING. `DocPath`, `DocBody` unchanged.
- `WriteOp.update(path, fields)` → `deleteFields: []`.
- **New `WriteOp.transition(path, fields, deleteFields)`** — a variant
  transition: sets every field of the new variant, removes every field of
  the old variant the new one does not declare. A key may not be in both
  `fields` and `deleteFields`: the factory returns the op as given (data,
  no validation), and every adapter and double refuses such a plan with
  `RepositoryError.writeFailed(path, 'field-set-and-deleted')`.
- **New pure helper `WriteOp.variantFieldsToDelete(before: DocBody, after:
DocBody): readonly string[]`** — the keys present in `before` and absent
  in `after`; systems call it to build a transition from two flat variants,
  so no system hand-lists stale fields.
- A `Set`/`Create` body never contains a deletion (it replaces the whole
  document).
