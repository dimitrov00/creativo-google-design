# Firestore runbook

**Date:** 2026-10-10 · **Status:** Phase 3a deliverable of `docs/architecture/ecs-migration.md` §6 Phase 3. It holds the reader matrix the 3b flips are cut from, the seven TTL policies, the deploy order and the per-flip grep gates. · **Law:** `CLAUDE.md` Laws 5 and 6, `.claude/rules/firestore-layout.md`. This runbook never overrides them.

**Law 6 and the flatten pass.** The blueprint's target spellings (`timeInterval.startMs`, `bookingStatus.kind`, `*MinorUnits` and so on) predate Law 6. The flatten pass decides the flat spellings (`*UtcMs`, `*Cents` + `currency`, SCREAMING_SNAKE domain-prefixed discriminators, root keys only). So this runbook names **today's** spellings: the ones each flip removes, whatever the flatten pass renames them to. Two things go further. The gate blocks marked _Law 6_ (§4) also catch the old money names and the generic `status`/`kind` keys, and the index gate flags any dotted path or generic discriminator. If the flatten pass keeps one of those names, or renames another field (for example `dayKey` → `localDate`, as Law 5's example spells it), it edits the lists in §4.0 in its own commit.

**Re-derive before every flip.** Line anchors are as of 2026-10-10 (the 3a tree, before any flip). The flip-1 rows were re-derived on 2026-10-16, after flip 1 landed, without line anchors; the flip-2 rows (`users`, `otps`, `impersonationSessions`) were rewritten on 2026-10-21 to the after-state of `docs/architecture/flips/flip-2-identity.md` §2 (bundle names included), without line anchors; the flip-3 rows (`loyaltyAccounts` … `invitations`) were rewritten on 2026-10-22 to the after-state of `docs/architecture/flips/flip-3-loyalty.md` §2, and the flip-4 row (`positions`, `courses`, `events`, with its new `locations` reader and §1.2 edge) on 2026-10-22 to the after-state of `docs/architecture/flips/flip-4-programs.md` §2, both with bundle names and without line anchors; the dormant rows still name 3a files, and where a row names a file flip 1 deleted (`audit-profile-changes.ts`, `run-backfill.ts`, …), its successor is in `docs/architecture/flips/flip-1-booking-core.md` §2. The pass-B rows (`auditLog`, `streakDefinitions`, `services`, `barbers`, `users/{uid}/notifications`, `impersonationSessions`, `users/{uid}/rewardProgress`, `rewardPrograms`, `settings`) were re-derived on the pass-B tree on 2026-10-24, without line anchors. Before each flip, run the searches of §1.4 again and update the rows that flip touches. The closure in §1.3 holds only while no new edge appears.

A composite added after the blueprint has no number (never reuse a dropped one such as #20): it is named by its collection group and key list, e.g. `auditLog: targetCustomerId ASC, recordedAtUtcMs DESC` (the five audit timelines, audit-hardening WS-7).

**The Audit column (audit-hardening WS-3) — who records a write, and how the writer is named.** **trg users** = the `auditProfileChanges` trigger (`fn:main.ts`, `users/{docId}`): one `PROFILE_*` row per write naming the changed profile fields, `roles` and `accountStatus` (with their before/after tags), never a value. **trg gov** = that collection's own `audit…Changes` trigger (`fn:main.ts`, `<collection>/{docId}`, the same one helper — `decodeDocumentChangeEvent` → `pl:audit-document-change.pipeline.ts`): one `GOVERNED_DOC_CREATED` / `_UPDATED` / `_DELETED` row per write, deletes included, naming the changed top-level fields (a delete the before-image's), never a value; a `customers` row targets the record. **pl `<file>`** = a pipeline that writes its own row (inside its act's commit, except `run-backfill`'s per-call row). **none (…)** = no row records the write, and why; **none (console)** = only the seed, the e2e support or the console writes it, unaudited. Each **trg gov** trigger reads both bodies of its collection's write, for the changed top-level field names only (`GovernedChangeSystem.changedFields`); the Readers column lists each collection's other readers. A trigger row names its writer from the event's auth context (`AuditSystem.writerOf`): a browser write is `USER` with the uid and **no role snapshot** — the event carries no claims, so an auditor never reads `USER` as "client" (a barber's note is `USER` too); an Admin-SDK or console write is `SYSTEM` / `ADMIN_SDK` (`SYSTEM` / `FIRESTORE_SYSTEM` for the platform itself); an unreadable context is a `SYSTEM` / `UNATTRIBUTED_*` source, never a guessed person. A pipeline's human writer is its own row: the callable's verified caller (`Actor.forCaller`), so the booking verbs, the owner's profile edit, the streak publish and the impersonation start / end name the person and role who acted. The `impersonationSessions` writers are the two impersonation callables only, each audited in its commit; the `auditLog` writers are the Admin SDK only (pipelines and triggers), create-only.

**The export's reads (audit-hardening Phase 3 WS-C, the GDPR export).** `exportClientData` (`fn:main.ts`, `fn:wire/privacy.wire.ts`) is the admin's callable: the caller's token claims AND stored `roles` must hold `admin` (`Roles.PRIVACY`, never the sysadmin; P3-RU-13), and `CLIENT_PRIVACY` must be on, else it refuses before the person is read (`PRIVACY_FORBIDDEN`, `PRIVACY_UNAVAILABLE`). `pl:export-client-data.pipeline.ts` then reads one person — the client record `customers/{customerId}` and the account it links (`record.userId`) — OUTSIDE any transaction, through `fn:adapters/firestore-privacy.adapter.ts` `firestorePrivacyPorts(db, guardOf, log)` (`ClientFootprintPorts & LoyaltyAccountReadPorts & ClientStatsLoadPorts`) and `fn:adapters/firestore-audit-read.adapter.ts` `firestoreAuditReadPorts(db)`: the rows above marked "the GDPR export". Every query is one equality or `array-contains` on a root field over its automatic single-field index (the audit timelines on their WS-7 composites) — no new composite, no `orderBy` (the system orders what it read). Every list is read with `limit` = the cap + 1: past `EXPORT_MAX_DOCUMENTS` (20,000 documents, audit rows included) or `EXPORT_MAX_BYTES` (4,194,304 UTF-8 bytes of the bundle) the call refuses `PRIVACY_EXPORT_TOO_LARGE` and writes nothing — never a truncated file. The answer is ONE canonical JSON bundle (`clientExportVersion` 1, `ClientExportSystem.bundleOf`) of what the reads found, withholding what is not provably the person's or is a bearer capability: every voucher `code`, a photo's tokenised `url`, a shared visit's other guests' labels (`PrivacyMarker`), a visit contact not provably theirs, the notes of a visit they did not sit alone, and the call's own row; the avatar is not exported (P3-L-5). ### 2.2 Declared in `firestore.indexes.json`, deployed with the indexes

The seven policies are deploy configuration (pass E, E-3; `docs/architecture/flips/pass-e-leftovers.md` DEP-3). `firestore.indexes.json` `fieldOverrides` holds one entry per group of §2.1:

```json
{
  "collectionGroup": "<group>",
  "fieldPath": "purgeAt",
  "ttl": true,
  "indexes": []
}
```

`firebase deploy --only firestore:indexes --project "$PROJECT_ID"` (§3 step 1) creates them. `ttl: true` is the Firebase CLI's field-override flag, and `"indexes": []` is the `purgeAt` single-field index exemption of §2.4. The CLI writes both in one patch of `collectionGroups/<group>/fields/purgeAt` (firebase-tools 15.31.0, `lib/firestore/api.js` `validateField` / `patchField`), and it skips a field whose TTL flag and indexes already match the file. Deploy from an account allowed to change Firestore field configuration (Owner, or the Cloud Datastore Index Admin role). `.firebaserc` still names the placeholder `creativo-replace-me`, so set the real id first (`PROJECT_ID=your-firebase-project-id`). A policy may be enabled before any document carries the field. It then simply finds nothing to delete. Adding a TTL group means adding its entry to `firestore.indexes.json` in the same change as its stamp (`RetentionGroup`, `purgeAtFor`).

Fallback, only for a project the Firebase CLI cannot reach, one group at a time (it sets the policy alone; the next `firestore:indexes` deploy adds the exemption):

```bash
gcloud firestore fields ttls update purgeAt --collection-group="$GROUP" --enable-ttl --project="$PROJECT_ID"
```

### 2.4 What TTL does and does not promise

- Deletion is eventual: usually within a day of `purgeAt`, never at the instant. So no reader may rely on TTL for correctness. An OTP is refused on `expiresAt*` by `OtpSystem`, not by its absence. Busy and capacity readers start at today.
- A TTL delete is a real delete and fires the `onDocumentWritten` triggers of its path. Every TTL delete of a past `barberBusy` day fires `rebuildCapacityOnBusyChange` and `matchWaitlistOnBusyChange`. Both must keep the past-day early return (`rebuild-capacity.ts:84`; blueprint §4.1 adds it to `matchWaitlist`), or they rewrite retired months and spend reads for nothing. No trigger watches the other six groups.
- The emulator does not run TTL. The policies exist only in deployed projects.
- `purgeAt` carries no single-field index. Each group's §2.2 entry declares `"indexes": []` beside `"ttl": true` (pass E, E-3), following blueprint §3.4's precedent for never-queried fields. No query filters or orders on `purgeAt`: re-proved for pass E with `git grep -n "purgeAt" -- 'libs/**/*.ts' 'apps/**/*.ts' 'tools/**'`, which finds only the one stamp (`purgeAtFor`), comments and specs reading the stored value. Google's TTL guidance warns that an indexed timestamp TTL field with monotonically moving values can hotspot writes. A future query on `purgeAt` must first declare the index it needs in that group's entry. This runbook used to leave the exemption to the owner; pass E declares it and records that for the owner (pass-e plan §7.2 N-3).

**Erased persons (audit-hardening Phase 3 WS-D, the GDPR erasure).** `eraseClient` (§1.1 "The erasure's reads and writes") pseudonymizes the person's live documents and keeps their records: the visits, the money, the stats, the loyalty, the journal, the grants and vouchers and every `auditLog` row stay — ids, tags and amounts, never a name, a contact value or free text (the owner's answer of 2026-10-27; counsel to confirm that Art. 17(3)(b)/(e) covers the retained records and the windows below). What the erasure cannot reach ages out on its own clock:

- **PITR and the scheduled backups.** Firestore Point-in-Time Recovery keeps the pre-erasure versions for 7 days, a daily backup for 28 days. A restore from either brings the person's values back: after a restore, run `eraseClient` again for every person erased since the restored instant (the record's `erasedAtUtcMs` and the `PRIVACY_CLIENT_ERASED` rows name them).
- **Cloud Storage soft delete.** A deleted avatar or `SHOT` photo object — its `clientLabel` metadata included — stays restorable for the bucket's soft-delete window (7 days by default on a new bucket; `docs/production-deploy.md`'s backups item asks for a Storage policy).
- **OTPs that escape the sweep.** The sweep removes the sign-in challenges stored under the person's phones and e-mails before the stamp clears them. A challenge stored under another spelling (the trimmed RAW text, F2-10 — `request-otp.pipeline.ts`), or requested between the sweep and the stamp, keeps its `destination` until the `otps` TTL removes it (24 h past expiry, §2.1).
- **Logs.** No line carries a personal value (R36 / T5): the 30-day `_Default` bucket and the 400-day audit bucket hold the uid, the record id and the counts, which stay.

**Legal hold (the owner's procedure; nothing automates it).** A hold freezes what a TTL, a retention window or a person would otherwise delete. When the owner (or counsel) declares one, for named people or a date range:

1. **Firestore documents.** Export the affected collections before anything purges them: `gcloud firestore export gs://<hold-bucket>/<case> --collection-ids=<ids> --project="$PROJECT_ID"`, into a Cloud Storage bucket the hold alone uses, then place the objects under a hold (`gcloud storage objects update gs://<hold-bucket>/<case>/** --temporary-hold`). For a TTL group whose documents must stay live, disable that group's policy for the hold's length (§2.2's fallback line with `--disable-ttl`) and record the change; re-enable it with `--enable-ttl` when the hold lifts. `auditLog` and `triggerFailures` need no step: nothing deletes them.
2. **Logs.** Copy the matching entries out of the audit bucket before their 400 days run out: `gcloud logging copy creativo-audit-400d gs://<hold-bucket>/<case>-logs --location=global --log-filter='<the case filter>' --project="$PROJECT_ID"`, then hold the objects as above. Entries older than 30 days exist only in the audit bucket; client issues (30 days in `_Default`) cannot be recovered after that.
3. **Backups.** A scheduled backup expires at its 28 days; restore the relevant one into a separate database (`gcloud firestore databases restore`) and export it as in 1 if the hold reaches back further than PITR's 7 days.
4. Write the hold down (who asked, what is held, where, until when) beside the case; lifting it is the reverse, in the same record.

- **The predeploy.** `firebase.json` runs it before every hosting deploy (`--scope web`: P1–P6, over the very build the deploy uploads) and last in the functions predeploy (`--scope functions`: P1–P3 and P6–P9), on the project the CLI deploys to (`$GCLOUD_PROJECT`). Flip 4 is the first runtime reader of that constant. The preflight's P1 checks it. DEFAULT_LOCATION_ID=loc-center   # TenantConfig.DEFAULT.defaultLocationId

1. **Indexes first, additive.** Run `firebase deploy --only firestore:indexes --project "$PROJECT_ID"`. When the CLI offers to delete indexes the project has but the file does not, answer **No** here, because code still running may query them. The same deploy writes the seven TTL policies and their `purgeAt` exemptions (§2.2); if it also offers to delete field overrides the file does not hold, answer **No** as well. Then wait until every composite is `READY`: the preflight's P3 row reads `PASS` (`pnpm run preflight --project "$PROJECT_ID"`), and it names each composite still building. Fallback, with gcloud:

   ```bash
   gcloud firestore indexes composite list --project="$PROJECT_ID" --format="table(name.basename(),collectionGroup,state)"
   ```

   A function or page that queries before its composite is `READY` fails with `FAILED_PRECONDITION`. The emulator never enforces composites, so this failure is invisible locally. Examples: the capacity rebuild's range reads on #13 and #16, the matcher's #14 and #15, the booking and history reads on #6, #7, #18 and #19, `/careers` on #12 (re-keyed to `positionStatus, sortOrder` by flip 4), and the admin's audit timelines on the five unnumbered `auditLog` composites — `targetCustomerId`, `targetUserId`, `resourceId`, `actorUserId` and `actorAdminUserId`, each `ASC` then `recordedAtUtcMs DESC` (audit-hardening WS-7; `tools/verify/indexes/audit-indexes.spec.mjs` pins them declared). `auditOperationId` keeps its automatic single-field index: never put it, or `resourceId`, in a `fieldOverride`.

2. **Rules.** Run `firebase deploy --only firestore:rules,storage --project "$PROJECT_ID"`. Rules ship before the code that depends on them, such as the notifications owner rule on the renamed read stamp (flip 1) and `couponGrants` `allow update: if false` (flip 1). `storage.rules` is unchanged by the migration but deploys with them.
3. **TTL.** TTL is deployed with step 1 (§2.2: the seven `purgeAt` entries of `firestore.indexes.json`). Pass §2.3 (all seven `ACTIVE`: the preflight's P2) before step 4; the functions predeploy refuses step 4 until P2 passes. After the first deploy, re-run §2.3 only when a policy is added.
4. **Functions.** Run `firebase deploy --only functions --project "$PROJECT_ID"`. The `predeploy` hook in `firebase.json` builds them, writes the flags env file, and runs the preflight (`--scope functions`: P1–P3 and P6–P9).

   **The walk-in id key (OR-26, once per project, before the first functions deploy).** `commitBooking` and `staffEditAppointment` key a walk-in's record id (`CustomerId.forWalkIn`) with HMAC-SHA-256 under the Secret Manager secret `WALKIN_ID_KEY`, so the id never gives the guest's phone or e-mail back. Create it with a random value: `openssl rand -hex 32 | firebase functions:secrets:set WALKIN_ID_KEY --data-file=- --project "$PROJECT_ID"`. Never rotate it once walk-ins exist: a new key mints new ids, and the desk then meets every returning walk-in as a new record. A function bound to it refuses to key with an empty value (a defect, never an unkeyed id). The emulator never reads Secret Manager: `tools/flags/write-functions-env.mjs` writes a fixed TEST value into the build's `.secret.local` for a `demo-*` project, and `firebase.json` never deploys that file.

   **The log digest key (audit-hardening WS-4.2, once per project, before the first functions deploy that binds it).** Every callable but `reportClientIssues` binds the Secret Manager secret `LOG_DIGEST_KEY`: its one `callable.completed` / `callable.refused` / `callable.failed` outcome line carries `inputDigest`, an HMAC-SHA-256 (cut to 16 hex characters) of the decoded command's allowlisted ids, codes and numbers under this key, so two calls with the same input can be told apart without the input in the log. Create it with a random value: `openssl rand -hex 32 | firebase functions:secrets:set LOG_DIGEST_KEY --data-file=- --project "$PROJECT_ID"`. A deploy of a function bound to a secret that does not exist fails. An empty value is no defect: the line prints `inputDigest: null` and the call still answers. Rotating it only changes the digests from then on (they join calls, never documents). The emulator reads the fixed TEST value `tools/flags/write-functions-env.mjs` writes into `.secret.local`, as for the walk-in key.

5. **Hosting.** Run `pnpm nx build web`, then `firebase deploy --only hosting:web --project "$PROJECT_ID"`. The hosting `predeploy` runs the preflight over that build (`--scope web`: P1–P6), so P4 judges the very files the deploy uploads.
6. **Prune.** Once functions and hosting are live, run `firebase deploy --only firestore:indexes --project "$PROJECT_ID"` again and answer **Yes** to deleting the indexes the file dropped, for example #20 in flip 1 and #12's old `status, sortOrder` key in flip 4. `--force` answers yes without asking. The preflight's P3 lists every such index as an `INFO` prune candidate until then.

   **Pass B's deleted composites #1, #3 and #9 (OR-36).** Pass B (`6b1a7a81`) deleted three composites with the catalogue streams' never-passed `categoryId` / `locationId` filters. On a project last deployed from a tree older than `6b1a7a81`, this prune deletes them, after the web build that drops the filters is live; P3 lists them until then. A first deploy has nothing to prune: no hosted project has ever existed (`.firebaserc` names the placeholder).

7. **The metrics and alerts (OR-34 and audit-hardening WS-6, once per project, the owner's).** After step 4, run `tools/ops/log-metrics.sh --project "$PROJECT_ID"` (a dry run: it prints every metric's config and every command, and runs nothing), then the same with `--apply`. It creates or updates five logs-based counters — `client_issue_count` (OR-34's recipe that this step used to spell out: filter `jsonPayload.clientIssueKind:*`, label `kind`), `trigger_attempt_failed` (labels `outcome`, `fn`), `document_refused`, `audit_actor_missing` and `callable_failed` (label `callable`), each server metric filtered on one `LogEvent` message — and the alert policies of `tools/ops/alerts/*.yaml` (client issues above 100 per 5 minutes, as before; any PERMANENT trigger attempt or more than 10 failing in 5 minutes; any refused document; any act without its audit row; more than 5 failures of one callable in 5 minutes). Attach an e-mail notification channel to each policy in Cloud Monitoring → Alerting. `tools/verify/ops/ops-scripts.spec.mjs` holds every message a filter names to a value of `libs/ecs-core/src/primitives/log-event.data.ts`, so renaming an event fails a spec instead of silencing its alert. The privacy-policy line the ruling names ("diagnostic data under legitimate interest, 30-day Cloud Logging retention, no personal identifiers") is the owner's to publish.
8. **The platform backstops (audit-hardening WS-6, once per project, each an owner decide item of `production-deploy.md` §1).** Three scripts, each idempotent and a dry run unless `--apply` is passed (it prints its `gcloud` commands, and the probe that picks create or update, and runs nothing): `tools/ops/firestore-backups.sh` (Point-in-Time Recovery on, 7 days; a daily backup schedule kept 28 days — best before the hand-written bootstrap of `production-deploy.md` §2, which has no other undo), `tools/ops/audit-logs.sh` (Cloud Audit Logs Data Access `DATA_WRITE` and `ADMIN_READ` for `datastore.googleapis.com` — the name that covers Firestore, plan RU-34 — and `identitytoolkit.googleapis.com`, unconfirmed; a read-modify-write of the IAM policy's `auditConfigs` under its etag; read its volume and billing note first) and `tools/ops/log-sink.sh` (the 400-day bucket `creativo-audit-400d` and the sink `creativo-audit-sink`, §2.5; `--lock` locks the bucket and is **irreversible**: never implied, only on the owner's word). ## 4. Per-flip grep gates

A flip passes its gate when no surviving file names a field the flip removed. Each gate runs **after its flip lands, with every earlier flip already landed**. On the 3a tree every gate failed; that is the "before" state they prove away. Flip 1's gate passes since flip 1 landed (§4.1). The hard scope `STORE` is every file that touches a stored body: handlers, both adapter trees, seed, e2e support, P0 proofs and rules. The blueprint's gate scope listed only `apps/functions/src/{lib,adapters}`, `libs/infrastructure`, web stores and the seed, which leaves out the e2e support and the P0 proofs (§1.3 (1)–(2)). Stores and components get a **review** list rather than a hard gate. In those files a hit is either a read of the flipped entity, which the flip fixes, or a view-model, callable or draft name, which Phase 4 retires; the reviewer records which. A hit in a comment counts: a comment naming a removed field is stale.

Paste §4.0 once per shell (bash or zsh), then the block of the flip. Every block was dry-run on 2026-10-10 under both shells: each gate reports `FAIL` on today's tree and none reports `ERROR`. The committed runner `tools/verify/runbook-gates/run-gates.mjs` (`pnpm nx run verify-tools:runbook-gates`, or `pnpm run verify:runbook`; never cached, run alone on a clean tree) reads these blocks from this file at run time — it holds no copy of a gate — and runs §4.0 plus each of §4.2–§4.5 and §4.7–§4.10 alone under bash, failing on any `FAIL`, any `ERROR`, a block that prints no `ok` or no `gate: PASS` line, and an untracked file a block leaves behind.
