# Firestore runbook

**Date:** 2026-10-10 · **Status:** Phase 3a deliverable of `docs/architecture/ecs-migration.md` §6 Phase 3. It holds the reader matrix the 3b flips are cut from, the seven TTL policies, the deploy order and the per-flip grep gates. · **Law:** `CLAUDE.md` Laws 5 and 6, `.claude/rules/firestore-layout.md`. This runbook never overrides them.

**Law 6 and the flatten pass.** The blueprint's target spellings (`timeInterval.startMs`, `bookingStatus.kind`, `*MinorUnits` and so on) predate Law 6. The flatten pass decides the flat spellings (`*UtcMs`, `*Cents` + `currency`, SCREAMING_SNAKE domain-prefixed discriminators, root keys only). So this runbook names **today's** spellings: the ones each flip removes, whatever the flatten pass renames them to. Two things go further. The gate blocks marked _Law 6_ (§4) also catch the old money names and the generic `status`/`kind` keys, and the index gate flags any dotted path or generic discriminator. If the flatten pass keeps one of those names, or renames another field (for example `dayKey` → `localDate`, as Law 5's example spells it), it edits the lists in §4.0 in its own commit.

**Re-derive before every flip.** Line anchors are as of 2026-10-10 (the 3a tree, before any flip). Before each flip, run the searches of §1.4 again and update the rows that flip touches. The closure in §1.3 holds only while no new edge appears.

## 2. TTL policies

Firestore TTL deletes a document once the `Timestamp` in its TTL field is in the past. The policy is set per **collection group**, so `notifications` covers every `users/{uid}/notifications`. `purgeAt` is the one `Timestamp` a document holds. It is a root field stamped by the adapter, outside the entity type (`.claude/rules/firestore-layout.md`). The seven groups match the rule's list one for one.


- A group missing from the list was never enabled.

The tab must list all seven `(group, purgeAt)` pairs, each in the active state. This check is a **release gate for the first production deploy**: do not run step 4 of §3 until all seven read ACTIVE.

### 2.4 What TTL does and does not promise

- Deletion is eventual: usually within a day of `purgeAt`, never at the instant. So no reader may rely on TTL for correctness. An OTP is refused on `expiresAt*` by `OtpSystem`, not by its absence. Busy and capacity readers start at today.
- A TTL delete is a real delete and fires the `onDocumentWritten` triggers of its path. Every TTL delete of a past `barberBusy` day fires `rebuildCapacityOnBusyChange` and `matchWaitlistOnBusyChange`. Both must keep the past-day early return (`rebuild-capacity.ts:84`; blueprint §4.1 adds it to `matchWaitlist`), or they rewrite retired months and spend reads for nothing. No trigger watches the other six groups.
- The emulator does not run TTL. The policies exist only in deployed projects.
- `purgeAt` keeps its default single-field index today, and no query filters on it. Google's TTL guidance warns that an indexed timestamp TTL field with monotonically moving values can hotspot writes. A `fieldOverrides` entry `{ "fieldPath": "purgeAt", "indexes": [] }` per group would follow the precedent of blueprint §3.4. It is not in §3.4, so it is the owner's call, not a step of this runbook.

## 3. Deploy order

This order applies to the **first production deploy**. It also applies to every deploy of a 3b flip to a non-emulator project. `pnpm run seed:dev` refuses to run outside the local emulators (`tools/seed-dev-catalog.mjs:150-153`), so a hosted dev project is wiped and repopulated by hand, never by the seed.

1. **Indexes first, additive.** Run `firebase deploy --only firestore:indexes --project "$PROJECT_ID"`. When the CLI offers to delete indexes the project has but the file does not, answer **No** here, because code still running may query them. Then wait until every composite is `READY`:

   ```bash
   gcloud firestore indexes composite list --project="$PROJECT_ID" --format="table(name.basename(),collectionGroup,state)"
   ```

   A function or page that queries before its composite is `READY` fails with `FAILED_PRECONDITION`. The emulator never enforces composites, so this failure is invisible locally. Examples: the capacity rebuild's range reads on #13 and #16, the matcher's #14 and #15, the booking and history reads on #6, #7, #18 and #19.

2. **Rules.** Run `firebase deploy --only firestore:rules,storage --project "$PROJECT_ID"`. Rules ship before the code that depends on them, such as the notifications owner rule on the renamed read stamp (flip 1) and `couponGrants` `allow update: if false` (flip 1). `storage.rules` is unchanged by the migration but deploys with them.
3. **TTL.** Run §2.2, then pass §2.3 (all seven `ACTIVE`). After the first deploy, re-run §2.3 only when a policy is added.
4. **Functions.** Run `firebase deploy --only functions --project "$PROJECT_ID"`. The `predeploy` hook in `firebase.json` builds them and writes the flags env file.
5. **Hosting.** Run `pnpm nx build web`, then `firebase deploy --only hosting:web --project "$PROJECT_ID"`.
6. **Prune.** Once functions and hosting are live, run `firebase deploy --only firestore:indexes --project "$PROJECT_ID"` again and answer **Yes** to deleting the indexes the file dropped, for example #20 in flip 1. `--force` answers yes without asking.

In short: indexes and rules always go before functions, and TTL is `ACTIVE` before the first production deploy of functions.
